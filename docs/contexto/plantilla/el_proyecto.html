1 Qué es

Dos jugadores cargan una sola caja al mismo tiempo. Si uno avanza y el otro no, la caja se tuerce. Si se tuerce mucho, se cae o se daña. La idea es ir juntos.

El enemigo no es el mapa: es no botar, no mojar, no soltar.

Controles: P1 WASD + Espacio P2 Flechas + Enter

Mecánicas (en simple)

Qué pasaEn palabras de jugador
Se tuerceSi no se mueven a la vez, la caja se inclina. Si se inclina de más, la sueltan.
Se vacíaCuando va torcida, el contenido se sale por un huequito.
Se mojaAgua, lluvia o chorros la empapan: pesa más y se descontrola.
Van juntosSi los dos se coordinan, van más rápido y la caja se endereza.

Las tres cajas

Misma regla (cuidarla entre dos). Cambia qué castiga más cada una:

Caja VIP

Cartón fino. Se inclina, se fuga y se moja fácil. Ideal para aprender.

Caja del gato

Trae gato. Si se desesperan o se desincronizan, araña la caja.

Caja bomba

Tiene tiempo. El desorden y el agua la dañan; si llega a cero, explota.

Los cuatro mapas

Son los niveles de campaña. Cambia el paisaje y los obstáculos; la caja sigue siendo la misma regla.

MapaBiomaQué se siente
El MuelleMarPrimer turno: cangrejo, perro, aguacero. Arriba el ron.
La BahíaMarMás larga y mojada: rieles, ferries, olas.
La AldeaSelvaBaldados y vidrio mentiroso (uno aguanta, el otro no).
El CampamentoDesiertoCactus, coyote y dos caminos: uno se corta.

Cómo nos organizamos (flujo)

Jose, Luis y Danel desarrollan juntos. No es una cadena “creativo → Luis → Jose → Danel”. El día a día de código es colaborativo.

Núcleo: Jose · Luis · Danel (desarrollo en conjunto)
  • Jose cierra alcance y merge/deploy; también programa.
  • Luis trae contexto externo y programa UI/producto.
  • Danel empuja el runtime del juego y estabiliza lo jugable.
  • Creativos aportan playtests, briefs y propuestas (docs). El núcleo decide qué entra al build.

4 Cómo está partido el código

No es el monorepo ni el scaffolding del repo. Es cómo separamos el juego en sí para no romper todo al cambiar una cosa:

  • input — teclado
  • sim/ — reglas (caja, vidas, fallos) sin dibujar
  • view/ — PlayCanvas dibuja lo que la sim dice
  • ui/ — menú / HUD / ganar-perder

Así se puede tunear la caja sin rehacer el menú, y al revés. Cuando el monorepo y el backend nuevo entren, esta sección se actualizará (carpetas y deploy); la idea de “reglas vs vista” puede quedarse.

Historia de construcción

  1. Reunión presencial del equipo: cada uno expuso ideas para un juego y elegimos el camino juntos.
  2. Jam Better Together → dos en un teclado + caja compartida.
  3. Primer nivel jugable: inclinación, huequito, mojado.
  4. Clima, rieles, NPCs y los cuatro mapas.
  5. Menú, personajes, audio, ranking y publicación.
  6. Ahora: producto online (local + multi) encima de ese piso.

5 Cómo trabajamos en GitHub

El repo es la fuente de verdad. No se sube “a dedo” a producción: todo pasa por ramas, pull requests y revisión.

Ramas

RamaPara qué
devIntegración del día a día. Aquí aterrizan los PRs del equipo.
mainProducción (GitHub Pages). Solo entra lo que Jose promueve cuando toca desplegar.
issue/N-slugTu trabajo de una issue concreta. Sale desde dev.

Flujo de un cambio

  1. Toma (o te asignan) una issue en GitHub.
  2. Crea la rama desde dev: issue/63-auth
  3. Trabaja, haz commits claros, abre un Pull Request hacia dev.
  4. CI / revisión. Si está bien, se mergea a dev.
  5. Cuando toque publicar, Jose lleva dev → main (deploy).

6 Qué sigue (objetivos)

El piso local ya existe. Lo que viene es producto, pulido y usabilidad — no reescribir el juego desde cero.

Producto expo (prioridad cercana)

Local

Mismo PC, dos jugadores. Sin login obligatorio.

Multijugador

Dos PCs: cuenta, salas, sync y micro.

Móvil

Pantalla Coming soon (aún no se juega en teléfono).

Ranking

Puntajes local y multi separados.

Issues de producto/tech en GitHub: #63–#68. Docs creativas: #69–#71.

Más allá del multi (posibilidades abiertas)

  • Refactors visuales de mapas y jugadores (mismo feel, mejor lectura).
  • Pantalla de configuración multijugador con identidad propia (no un menú genérico).
  • Usabilidad probada: playtests formales, hallazgos priorizados, iterar HUD y fallos.
  • Briefs de rediseño por mapa (después del multi, sin bloquear la expo).
  • Monorepo + backend actualizado (cuando Jose lo active; actualizará rutas y deploy).

Regla: no se tira el coop local ni la caja para “hacer online”. Se suma encima.
